# 案例实测 2：合同管理 2000+ 合同 × 50 管理员「后期卡死」

场景：比赛后期合同 2000+、管理员 50+，打开合同列表/详情特别容易卡死。
栈：Django + DRF + PostgreSQL（比赛库 comp_<id>）。

## 归因（静态分析 + 基线压测）

静态分析（第 1 步 SQL 层）直接命中 3 个热点：

| 热点 | 代码病灶 | 量级 |
|------|---------|------|
| **N+1 变体** | `_party_data` 每合同每参与方 `Company.objects.filter(pk=...)` | 2000 合同 × 2 方 = **~4000 次查询/请求** |
| **全表拉回 Python 过滤** | `_visible_contracts` 把所有合同读回内存再按 parties 过滤 | 每请求全表读取 |
| **无分页全量 JSON** | 列表 `[:500]` 且每行带 inputs/parties 全量字段 | 大 JSON 序列化 |

基线压测（50 管理员 × 1.5s 思考时间，稳态）：

| 接口 | P50 | P95 |
|------|-----|-----|
| 合同列表 | **6,991ms** | **14,220ms** |
| 合同详情 | 966ms | 2,550ms |
| 增量同步 | 892ms | 1,476ms |

（0 错误、QPS 15.8 —— 慢而不崩，正是"容易卡死"的形态。）

## 修复（按 skill 修复清单 4/5）

1. **消 N+1**：`_company_map_for(contracts)` 批量一次查询 → 传 `company_map` 给序列化
   （列表/增量/详情全部改造；4000 次查询 → 1 次）。
2. **可见性过滤下推 DB**：`parties__contains=[{"companyId": N}]`（JSONB containment）
   + **GIN 索引** `idx_contract_parties_gin (parties jsonb_path_ops)`；
   迁移存量库用一次性脚本 `scripts/migrate_competition_dbs.py`。
3. **服务端分页 + 字段裁剪**：`?page&pageSize&status&q`，默认 50/页；列表/增量走 `thin`
   序列化（不带 inputs 等大字段，详情才带）。
4. 前端适配：表格只渲染当前页 50 行 + el-pagination；过滤条件服务端化（关键字 300ms 防抖）；
   WS 信号仍走增量按 id 幂等合并。

## 修复后（同压测口径，全部 PASS，0 错误）

| 接口 | P50 | P95 | 提升 |
|------|-----|-----|------|
| 合同列表 | **34.3ms** | **200.7ms** | P50 **≈205×** |
| 合同详情 | 40.3ms | 356.9ms | ≈24× |
| 增量同步 | 27.9ms | 175.2ms | ≈32× |
| 首屏加载（预热） | 786ms | 1,010ms | ≈10× |

吞吐 15.8 → **92.7 QPS**；真实节奏（1.5s 思考）50 管理员负载 ~33 QPS，余量 ~3×。

## 教训

1. **列表页 N+1 是"后期卡死"的头号惯犯**——数据量小时无感，翻倍到 2000 就是秒级灾难；
   常规体检：对每个列表接口数一下 SQL 条数（Django debug toolbar / `connection.queries`）。
2. **JSON 列做可见性过滤必须配 GIN 索引并下推 DB**，Python 过滤等于全表扫描。
3. **列表响应字段裁剪**（薄字段）与分页同等重要：50 行 × 全量 JSON 也会拖慢序列化。
4. 改完**存量库要补迁移**（新索引不自动落到老库），否则压测数字不体现优化效果。
