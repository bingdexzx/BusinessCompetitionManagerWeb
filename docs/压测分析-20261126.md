分接口特征：

- 19 个全局接口 P50 普遍在 **1.1–1.4s**，P95 在 **2.3–6.1s**；
- `网络日志` 最慢：P50 **6.5s**，P95 **84.7s**，Max **162.9s**；
- 所有接口都出现 **504**，健康检查也出现 504（178 次）；
- P99 约 **60.9s**，与常见的 60s 代理超时高度吻合。

## 2. 结论：不是单接口慢，是整体容量被打满

### 2.1 请求量已超过服务能力

500 并发、思考 0.5s，按 19 个接口一轮，理论请求量约 **300–400 req/s**；
实际只有 **102.8 QPS**，说明请求在 nginx / waitress / DB 前排队。

按 Little's Law：

```
在途请求 ≈ QPS × 延迟 = 102.8 × 1.23 ≈ 126
```

而 HTTP 处理线程只有 `4 worker × 8 threads = 32`，其余都在排队，最终触发 60s 超时。

### 2.2 健康检查也被拖慢

`/api/health` 本身不查业务库，P50 却到 **1.44s**、P95 **46.6s**，说明瓶颈在：

- 请求线程被慢请求占满；
- 每个请求同步写 `NetworkLog`（全局库）；
- 数据库连接/写入排队，而不是健康检查逻辑本身。

### 2.3 `网络日志` 是线程黑洞

`/api/logs/network` P50 6.5s，远高于其他接口。其实现每次执行：

```python
total = qs.count()          # 对按月分区的日志表做 COUNT(*)
rows = qs.order_by('-occurred_at')[offset:offset + limit]
```

在日志量大的生产库上，`COUNT(*)` 很贵；慢查询长期占用线程和 DB 连接，进一步放大排队。

### 2.4 504 是超时结果，不是真实业务延迟

P99≈60s、多个接口出现 504，说明上游等待超过代理超时；此时：

- **调大 nginx 超时只会让用户等更久**，不会提升吞吐；
- 应优先降低排队（容量、慢请求、日志写入）。

## 3. 已做的低风险优化

| 改动 | 作用 |
| --- | --- |
| 网络日志异步批量写 | 请求线程不再同步写全局库，后台每 100 条/200ms `bulk_create` |
| `/api/health` 绕过背压/限流/网络日志 | 健康探针不占 DB 连接与审计写入 |
| `/api/update-logs/latest` 缓存 15s | 高频轮询不再每次查库 |
| 网络日志 `occurred_at` 倒序索引（迁移 0004） | 翻页不再全表排序 |
| 日志 API 改 keyset 分页 | 返回 `hasMore/nextCursor`，彻底去掉精确 `COUNT(*)`；前端改「加载更多」 |
| 插件注册表缓存 15s | 高频只读列表少查库 |
| 比赛列表 / 学校列表缓存 | `/api/competitions` 10s（按用户）、`/api/schools` 30s，写操作失效 |
| 压测报告补「计划时长」 | 区分计划时长与实际 186s |
| 结论增加 504 / P99≥30s 提示 | 直接把「超时」与「容量」关联起来 |

以上为应用侧低风险改动，仍需重新部署后复测。

## 4. 建议的优化顺序

### P0：先把慢请求和日志写入从热路径拿开

1. **网络日志异步化/批量写（已落地）**
   - 请求线程只入内存队列，后台线程每 200ms 或每 100 条 `bulk_create`；
   - 队列满时丢弃并计数，避免拖垮业务；
   - 进程退出与测试库销毁前 flush。
2. **日志查询去掉精确 COUNT（已完成）**
   - `occurred_at` 倒序索引 + keyset 分页；
   - API 返回 `hasMore/nextCursor`，前端「加载更多」；
   - 不再执行 `COUNT(*)`。
3. **健康检查彻底旁路**
   - `/api/health` 不经过认证、网络日志、数据库连接池，直接返回。
4. **只读全局接口缓存（已完成）**
   - `plugins` 15s、`update-logs/latest` 15s、`competitions` 10s、`schools` 30s；
   - 写操作失效或短 TTL；测试环境跳过缓存。

### P1：容量与连接池

1. 确认生产 CPU 核数与 `run_servers.py --workers/--threads`：
   - 当前 32 线程；先观察 CPU 是否打满、DB 是否成为瓶颈；
   - 加线程前先确认 `max_connections`、PgBouncer `default_pool_size`、
     `DB_MAX_CONCURRENT_REQUESTS` 的预算。
2. 检查 nginx 实际 `proxy_read_timeout`：
   - 报告 P99≈60s，与仓库配置的 300s 不一致，可能被 1Panel/OpenResty 覆盖；
   - 统一配置并记录，避免「以为是业务慢，其实是代理超时」。
3. 观察压测期间服务端：
   - CPU、内存、PG 连接数/锁等待、PgBouncer `SHOW POOLS`、nginx 5xx。

### P2：压测方法

1. **500 并发单客户端过重**：单进程 Python 线程可能先打满客户端；
   建议多台压测机，或单机从 100 并发逐步加。
2. **用 RPS 模式找拐点**：

   ```bat
   --mode rps --rps 50  --duration 60 --users 100
   --mode rps --rps 100 --duration 60 --users 100
   --mode rps --rps 150 --duration 60 --users 100
   ```

   直到实际 QPS 明显低于目标，或 P95/504 持续上升。
3. **带上比赛 ID**：当前 `比赛范围：未指定`，只测了 19 个全局接口；
   加 `--cid` 才会覆盖公司、合同、股票、数据管理等比赛内接口。
4. **固定请求数模式做版本对比**：同一 `--users`、`--requests` 跑升级前后。

## 5. 复测验收标准

优化后重新跑同一组参数，至少观察：

- 500 并发下 P50 是否从 1.2s 降到 300ms 以内；
- 504 是否消失；
- 102.8 QPS 是否提升，或同 QPS 下 P95 是否下降；
- `/api/logs/network` 是否不再是 P50 最慢的接口；
- 500 并发下的客户端 CPU 是否已接近打满（确认不是压测机瓶颈）。

> 建议在 staging 复测，不要直接在生产上反复加压。生产只做小流量验证与监控。
