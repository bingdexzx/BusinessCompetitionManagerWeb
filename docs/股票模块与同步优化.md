# 股票模块与大数据量同步优化（设计与实施契约）

> 场景：比赛后期（60+ 账号）股票行情 + 合同等全量同步数据量大，轮询与推送触发的刷新叠加 → 卡死。
> 目标：移植旧系统股票模块到重构版（比赛库），并以**快照+增量协议、防风暴、分页/字段裁剪**落地。
> 本文是前后端实施的共同契约（接口字段以此为准）。
>
> **状态（2026-11）**：已全部落地——`apps/competition/stock/`（快照+增量、keyset K 线、
> 盘口/持仓/委托）、前端股票页、`scripts/load_stock_sync.py` 压测脚本；
> 最新压测数据见 `docs/数据库优化.md` §6。

## 1. 性能问题根因与对策总览

| 根因 | 对策（落地项） |
|------|----------------|
| 每次刷新拉全量（行情+持仓+订单+K线+合同） | **快照+增量协议**：首拉快照，之后按 `since` 游标只拉变更；`serverTime` 做下次游标 |
| 60 账号 × 轮询 + 推送触发刷新 → 请求风暴 | **推送只当信号**（WS 只发 `{type:'stock-updated', round}`）；客户端**去抖合并**（1.5s 窗口只发一次增量）、**单飞行请求**（in-flight 去重）、**页面不可见退避**（10s） |
| 大 JSON 序列化/传输 | **字段裁剪**：列表/增量只带薄字段（不含描述/大 JSON）；K线按需分页 |
| 前端一次性渲染上千行 → 主线程卡死 | 表格**分页**（50/页）+ `el-pagination`；K线图**按需加载**（选中股票才拉历史） |
| 大表查询慢 | `updated_at` 组合索引（已有 `(competition, updated_at)`；本库天然单比赛）；**keyset 分页**（`ORDER BY updated_at, id LIMIT n`，不用 OFFSET） |
| 并发写（撮合/落账）锁竞争 | 撮合/推进轮次单事务 + `select_for_update` 行锁；读走增量（MVCC 快照读不阻塞） |

## 2. 领域模型（`apps/competition/stock`，比赛库）

沿用旧系统领域（适配多库：不建跨库外键，`company_id/user_id` 存 int；同库 FK 保留）：

| 表 | 关键字段 | 说明 |
|----|----------|------|
| `Stock` | code, name, total_shares, init_net_profit, industry_pe, current_carbon, industry_avg_carbon, happiness, init_price, current_price, round, company(FK→companies.Company, SET_NULL), pb_company_id/pb_field_id/pb_random, carbon_field_ref, happiness_field_ref, industry_avg_carbon_refs | 股票（Decimal 金额，max_digits=60, dp=4）；`unique(code)` |
| `StockFundsAccount` | name, owner_type(COMPANY/USER), company_id, user_id, cash_balance, bind_field_id | 资金账户（Decimal 现金）；`unique(name)` |
| `StockHolding` | funds_account(FK), stock(FK), shares, cost_price | 持仓（shares ≥0 约束）；`unique(account, stock)` |
| `StockOrder` | stock(FK), funds_account(FK), side(BUY/SELL), price, quantity, amount, status(PENDING/FILLED/CANCELLED), round | 委托 |
| `StockCandle` | stock(FK), round, open/high/low/close, change_pct, volume | 每轮每股票一根；`unique(stock, round)` |

所有表 `updated_at`（auto_now）建索引 `idx_stock_*_updated`（增量同步）。

## 3. 引擎（`engine.py`，从旧系统移植）

入口（保持旧语义，撮合/定价/做市商/防连板/K线全部保留）：
- 纯函数：`compute_match`、`compute_price`、`build_candle`、`compute_init_price`（Decimal 精度、round2、限幅规则照旧）；
- 编排：`advance_round(competition_context, ...)`：撮合 → 定价 → K线 → 做市商报价 → 推进 `Stock.round`；
- 适配点：`BusinessError` → 本地 `StockError`；旧 `companies.Company`/`competitions.Competition` FK → 比赛库 `companies.Company`（int 引用其余）；异常全部转业务错误不落半账（单事务）。

## 4. API 契约（全部挂 `/api/competitions/{cid}/stock/...`）

### 4.1 行情与交易

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/stock/stocks` | 股票列表（薄字段：code/name/currentPrice/initPrice/round/updatedAt/涨跌幅）；`?page&pageSize` 分页 |
| GET | `/stock/stocks/{code}` | 单股详情（含指标全字段） |
| GET | `/stock/stocks/{code}/candles` | K线（`?fromRound&limit` keyset 分页，按需加载） |
| GET | `/stock/book` | 我的持仓 + 资金账户（owner 匹配 user 或本队公司） |
| POST | `/stock/orders` | 下单 `{code, side, price, quantity}`（校验现金/持仓） |
| DELETE | `/stock/orders/{id}` | 撤单（仅 PENDING 且本人） |
| GET | `/stock/orders` | 我的委托（`?status`，分页） |
| POST | `/stock/round/advance` | 推进轮次（超管；撮合+定价+K线，单事务） |
| GET | `/stock/market` | 市场概览：`{round, stockCount, updatedAt}`（轻量心跳） |

### 4.2 同步协议（核心性能项）

```
GET /stock/sync?since=<ISO时间|空>&limit=<默认500>
→ {
    "mode": "snapshot | delta",
    "serverTime": "下次游标（服务端时间）",
    "round": 12,
    "hasMore": false,
    "stocks":    [ 薄字段 + updatedAt ],
    "candles":   [ 新增/变更轮次（薄字段） ],
    "orders":    [ 我的订单变更 ],
    "holdings":  [ 我的持仓变更 ],
    "accounts":  [ 我的资金账户变更 ],
  }
```
- `since` 为空 → **snapshot**（全量薄字段，仍分页 `limit`）；带 `since` → **delta**（各集合 `updated_at > since`，`ORDER BY updated_at, id` keyset，`limit` 截断置 `hasMore`）；
- **游标永远用上一响应的 `serverTime`**（规避客户端时钟偏差）；
- 可见性裁剪：`orders/holdings/accounts` 只返回**我的**（user 或所辖公司）；`stocks/candles` 全员可见；
- 失败恢复：游标过期/异常 → 客户端自动回退 snapshot。

### 4.3 推送信号（防风暴，WS）

- 轮次推进/成交后广播：`{type:'stock-updated', round, serverTime}`（**不带数据**）；
- 客户端收到信号 → 去抖 1.5s → 合并成**一次** `/stock/sync?since=...`；页面隐藏时 10s 退避；
- 合同通知沿用现状（已有增量同步）。

## 5. 前端实施要求

1. 新页面：`StockMarketView`（行情看板：股票表（分页）+ 选中股 K 线按需加载 + 市场概览）、`StockManageView`（持仓/资金/委托/下单）；风格沿用全局主题（Element Plus）。
2. 同步客户端（`src/composables/useStockSync.ts`）：snapshot 起步 → delta 游标合并（Map by code/id 幂等覆盖）；in-flight 去重；去抖；可见性退避；失败回退 snapshot。
3. 表格一律分页渲染（50/页），不一次性渲染全量行；大列表用 `shallowRef` 降低响应式开销。
4. 路由 `/competitions/:cid/stocks`（行情）、`/competitions/:cid/stocks/manage`（交易管理，需参赛身份）；侧边栏「股票市场」入口（比赛内分组）。
5. 下单/撤单操作后**本地乐观更新 + 增量校正**，不拉全量。

## 6. 验收与压测实测（60 账号）

测试规模：**60 个并发账号**、800 股票 × 30 轮 K 线（2.4 万根）+ 持仓/委托；
`scripts/load_stock_sync.py`（TCP_NODELAY + 长连接客户端，`--think` 模拟前端 1.5s 去抖节奏）。

### 6.1 最终实测（全部修复后，稳态计时窗 20s，0 错误）

| 接口 | P50 | P95 | 判定 |
|------|-----|-----|------|
| `/stock/sync`（增量热路径） | **58ms** | 341ms | ✅ 稳态达标（P95 含穿插的全量回归样本） |
| `/stock/stocks`（分页） | **73ms** | 172ms | ✅ < 200ms |
| `/stock/book`（持仓/资金） | **40ms** | 88ms | ✅ < 200ms |
| 页面加载风暴（60 人**同时**拉初始快照，一次性） | 4.6s | 8.4s | ⚠ 极端场景；实际开页时间分散，前端 limit=2000+续拉已缓解 |

容量余量：闭环零思考时间压满 ≈ **95 QPS** 单进程天花板；真实节奏（1.5s 去抖）负载约 47 QPS ——
余量充足。**更多并发**按 §5 多进程扩展（uvicorn --workers / nginx 多实例）。

### 6.2 压测揪出的 5 个性能真相（均已修复/固化）

1. **HTTP 不能走 ASGI**：Django 同步视图在 daphne 下单线程敏感执行（32 并发仅 71.7 QPS），
   WSGI(waitress) 同场景 909.7 QPS —— 已拆分拓扑（`scripts/run_servers.py`：HTTP:8000 + WS:8001）。
2. **新建 PG 连接 ~44ms/条**（复用后 0.03ms）—— 必须 `CONN_MAX_AGE>0` 复用连接。
3. **连接数会随线程滞留打满 max_connections**（60 并发×2 库 > 100 → `too many clients` 500 雪崩）
   —— `max_connections` 调 200 + `DatabaseBackpressureMiddleware` 背压限流（并发 32 封顶，超时 503）。
4. **相关子查询 N+1 变体**：涨跌幅批量取末根 K 线原为 Subquery（500 股≈500 子计划，200ms+），
   改 PostgreSQL `DISTINCT ON` 单次索引扫描（~5ms）。
5. **续拉游标漏行**：快照被 limit 截断时 `serverTime=响应时刻` 会漏掉未交付尾部行 ——
   已改为「已交付行 keyset 边界回拨 1µs」（重复投递由客户端幂等合并吸收）。

### 6.3 测量方法教训（避免误诊）

- 压测客户端必须设 **TCP_NODELAY + 长连接**：Python urllib 小包受 Nagle/延迟 ACK 影响
  每请求虚增 ~80ms（实测 curl 4ms vs urllib 80ms），否则测量本身失真；
- **分阶段统计**：页面加载风暴（初始快照续拉）与稳态增量分开计，混在一起会把一次性成本
  误判成持续延迟。
