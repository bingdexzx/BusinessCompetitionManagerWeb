# 压测验收报告（多核后端，2026-10）

> 方法论：`perf-loadtest-db-opt`（测量自检 → 分层归因 → 带思考时间的压测验收）。
> 压测对象：多进程 prefork 后端（`scripts/run_servers.py`）+ 股票同步热路径。
> 数据规模：60 账号 × 800 股票 × 30 轮 K 线（约 2.4 万行）+ 持仓/委托；机器 18 逻辑核 / 15.4GB。

## 1. 测量方法自检（防止误诊）

| 检查 | 结果 | 结论 |
|------|------|------|
| curl 对照（单发 vs 同进程 5 连发） | 单发 107–317ms（进程启动+握手）；同进程复用 45ms | 对照工具自身开销大，**结论以 keep-alive 压测客户端为准** |
| 压测客户端（keep-alive + TCP_NODELAY） | `/api/health` 单用户 P50=**1.2ms** | 比 curl 快，**测量端无虚增**（Nagle 假象排除） |
| DB 建连成本（skill `probe_tools connect-cost`） | 新建连接 P50=**36.4ms** vs 复用查询 P50=**0.03ms** | 必须 `CONN_MAX_AGE` 复用（已配置） |
| 分阶段统计 | 预热（页面加载风暴）与稳态计时窗**分列** | 见 §3 |
| 闭环 vs 真实节奏 | think=1.5s（前端去抖）与 think=0（容量）分别压 | 见 §3/§4 |

## 2. 多核扩展性（闭环，`/api/health` 全中间件）

| worker 配置 | 吞吐 | P50 | 加速比 |
|-------------|------|-----|--------|
| 1 worker × 4 线程 | 1,077 QPS | 14.6 ms | 1.00× |
| 2 worker × 4 线程 | 2,211 QPS | 7.0 ms | **2.05×** |
| 4 worker × 4 线程 | 4,006 QPS | 3.8 ms | **3.72×** |
| 12 worker × 8 线程 | ≈4,000–4,250 QPS | ~7 ms | 测试台饱和（见下） |

- 吞吐随核数**近线性**，0 错误；
- 12 worker 不再增长：**整机 CPU 95.7% 饱和**（服务进程 7.6 核 + 60 线程压测客户端 + PostgreSQL 同机），
  已做双客户端对照（2×16 用户 = 4,250 QPS，未翻倍）→ **瓶颈是本机自压自测的整机 CPU，不是服务端**；
  要测服务端绝对容量需压测机独立部署（skill 要求），本报告的容量数字视为**下限**。

## 6. 分层归因发现（本次压测揪出的三个问题）

### 6.1 `too many clients` 500 雪崩（连接预算，已加硬约束）

`--threads 16` × 12 worker = 192 线程 → 连接峰值 ≈ 192 × 2 = **384 > max_connections=200**，
压测中 315 个 500（`FATAL: sorry, too many clients already`）。
**规则**：`workers × threads × 2 + 余量 ≤ max_connections`（`CONN_MAX_AGE` 会让连接随线程滞留）。
**已修**：`scripts/run_servers.py` 启动时读取 PG `max_connections` 做**预算自检**，超限直接给安全参数建议。

### 6.2 sync 稳态 P95 尾延迟 = 背压信号量排队（不是 CPU/SQL）

60 账号时 P95=272.8ms（超脚本 200ms 目标），20 账号时 P95=39.9ms——负载相关。
归因：60 账号按同一节奏**每 1.5s 齐射一波**，瞬时并发超过每 worker 背压额度
（预算 64 ÷ 12 worker = 5/worker）→ 请求在信号量上排队，排队时间计入延迟。
把额度调到 8/worker（8 worker × 8 线程、预算 64）后 **P95 272ms → 69ms**，全绿。
**取舍**：背压排队是刻意设计（宁可排队不雪崩）；尾延迟与全局并发预算 `DB_MAX_CONCURRENT_REQUESTS`
同向可调，前提是不破 §5.1 的连接预算。

### 6.3 waitress `Task queue depth` 告警 = worker 线程池打满

该告警（waitress `task.py`）表示任务排队超过空闲线程数，突发下每 worker 线程要够（但受 §5.1 约束）；
它同时会刷屏 stderr，压测时注意采集端开销。

## 7. 建议（按收益排序，对齐 skill 修复清单）

1. **配置按公式走**：`workers × threads × 2 + 20 ≤ max_connections`；`DB_MAX_CONCURRENT_REQUESTS`
   建议 ≥ `workers × 每 worker 峰值并发`（本例 8×8=64）以压住尾延迟，二者冲突时优先守连接预算。
2. **PostgreSQL 参数**（当前均为默认值，按 skill 参数表）：
   `shared_buffers` 128MB → 内存 25%（约 4GB）；`max_wal_size` 1GB → 2–8GB；
   `work_mem` 4MB → 16–64MB（**×连接数放大，勿激进**）；`log_min_duration_statement=500ms` 定位慢查询。
3. **预热风暴**（60 账号同时首拉全量，P95 1.7s、max 2.9s）：首屏分批/客户端错峰，或服务端限制全量并发。
4. **压测机独立部署**后再测绝对容量；当前 626 QPS / 12× 余量是同机自压自测的**下限**。
5. 并发再上（>50 账号常态 / 连接吃紧）：PgBouncer(transaction pooling) → 读写分离，见 docs/数据库优化.md §5。
