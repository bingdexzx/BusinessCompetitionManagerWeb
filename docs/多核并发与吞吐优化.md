# 多核并发与吞吐优化（多进程 worker 模型）

> 配套代码：`scripts/run_servers.py`（prefork 启动器）、`scripts/server_workers.py`（worker 进程入口）、
> `apps/common/pg_channel_layer.py`（跨进程推送通道层）、`settings/base.py`（并发预算）、
> `scripts/load_throughput.py`（吞吐压测）。相关：`docs/数据库优化.md` §1.0。

## 1. 为什么单进程吃不满多核

| 事实 | 影响 |
|------|------|
| Python 有 GIL，**一个进程同一时刻只能有一个线程执行字节码** | waitress 多线程只是提高 I/O 并发，CPU 密集吞吐封顶在单核算力 |
| 实测闭环压测（`/api/health`，全中间件含网络日志写库） | 单进程吞吐天花板 ≈ **1077 QPS**（P50 14.6ms），再加线程/并发不涨 |
| Django 同步视图在 ASGI 下单线程敏感执行 | HTTP 必须走 WSGI（见 docs/数据库优化.md §1.0），但 WSGI 仍是单进程 |

**结论：要多核吞吐，必须多进程。** 线程数只用来覆盖 I/O 等待，进程数决定 CPU 上限。

## 2. 新拓扑：prefork 共享监听（多进程 accept，无代理层）

```
                    ┌───────────────────────────────┐
   /api/*  :8000 ──▶│ 监听套接字（启动器 bind+listen │──▶ worker 0 (waitress, threads) ─┐
                    │ 一次，N 个 worker 共享 accept) │──▶ worker 1 (waitress, threads) ─┤──▶ Django/PG
                    └───────────────────────────────┘   ...                            ─┘
   /ws/*   :8001 ──▶ daphne（1 进程，I/O 密集，信号型推送不吃 CPU）
```

- 启动器 `scripts/run_servers.py` 只 `bind()+listen()` **一次**，把监听套接字随
  `multiprocessing` 传给 N 个 worker（Windows/Linux 通用，waitress 官方 `Adjustments(sockets=[...])`
  机制，即 systemd socket activation 同款）；
- 内核把新连接分发给不同 worker → **HTTP 后端可以真正用满多核**；
- 无反向代理、无额外转发跳数；worker 崩溃由看护循环自动拉起，热重载滚动重启全部 worker。

**Windows 实测坑（已规避）**：同一个共享监听套接字被复制进多个进程后，**并发调用 `listen()` 会竞态**
（部分进程拿到 `WSAEINVAL`）。因此 `listen()` 只由启动器做一次，worker 侧用 `SO_ACCEPTCONN`
判定已监听即直接用（`server_workers._ensure_listening`）。

## 3. 实测吞吐（本机，2026-10，`/api/health` 全中间件、16 并发闭环、TCP_NODELAY+长连接）

| 配置 | 吞吐 | P50 | P95 | 加速比 |
|------|------|-----|-----|--------|
| 1 worker × 4 线程 | 1,077 QPS | 14.6 ms | 17.3 ms | 1.00× |
| 2 worker × 4 线程 | 2,211 QPS | 7.0 ms | 9.9 ms | **2.05×** |
| 4 worker × 4 线程 | 4,006 QPS | 3.8 ms | 5.8 ms | **3.72×** |

吞吐随核数**近线性**增长，错误 0。复现：

```powershell
.venv\Scripts\python.exe scripts\run_servers.py --workers 4 --threads 4 --no-reload --no-ws
.venv\Scripts\python.exe scripts\load_throughput.py --users 16 --duration 8
```

## 4. 多进程必须同步改造的四件事（本次已落地）

### 4.1 跨进程推送通道层（否则 WS 收不到消息）

channels 的 `InMemoryChannelLayer` **只在单进程内有效**：HTTP worker 与 WS 进程各自独立，
`messages.services._push` 的 `group_send` 消息**根本到不了 WS 进程**（即使旧的单 worker
HTTP/WS 分端口拓扑也已如此）。新增 `apps/common/pg_channel_layer.py`：

- 用 **PostgreSQL 做跨进程消息总线**（零新增中间件）：`gipfel_channel_group`（组成员）+
  `gipfel_channel_message`（消息邮箱，投递即删 `DELETE ... RETURNING`）；
- 每进程一条后台 drainer 线程按 `CHANNEL_POLL_INTERVAL`（默认 0.1s）批量拉取本进程持有的
  channel 消息，投递进 `asyncio.Queue`（不阻塞事件循环）；
- 切换：`CHANNEL_LAYER_BACKEND=postgres|redis|memory`（redis 需装 channels-redis 并配 `REDIS_URL`）。

验收（真实跨进程，已通过）：`scripts/smoke_channel_layer.py`（进程内 + 子进程 group_send）、
`scripts/ws_push_smoke.mjs`（HTTP 进程发站内信 → WS 客户端实时收到）。

### 4.2 动态比赛库注册的线程安全

`settings/databases.register_competition_db()` 在请求期动态注册 `comp_<id>` alias，
多 worker × 多线程下并发写 `settings.DATABASES` 需互斥（进程内 `threading.Lock`）；
每个 worker 进程各自注册自己那份配置，天然正确（惰性、成本≈0）。

### 4.3 背压预算按 worker 分摊（防止加核把 PG 打爆）

`DatabaseBackpressureMiddleware` 的信号量是**进程级**，多进程下如果不分摊，
N 个 worker 会把并发上限放大 N 倍 → 连接峰值突破 `max_connections`。
现在 `DB_MAX_CONCURRENT_REQUESTS`（默认 32）是**全局预算**，按 `WEB_CONCURRENCY`
分摊成 `DB_MAX_CONCURRENT_REQUESTS_PER_WORKER`，加核扩容不放大连接峰值。

### 4.4 连接数预算（多库路由下每请求最多占 全局库+比赛库 2 条连接）

```
max_connections ≥ 总并发线程 × 2 + 后台余量
   其中 总并发线程 = workers × threads（run_servers.py 默认自动 ≈ 32）
   例：4 worker × 8 线程 = 32 并发线程 → 预算 ≈ 32×2 + 20 = 84
```

`CONN_MAX_AGE=60` 复用会让连接随线程数滞留，所以必须先满足上式再谈复用；
不够时优先调 `max_connections` / 上 PgBouncer，见 docs/数据库优化.md §2/§5。

## 5. 启动与配置

```powershell
# 全自动：HTTP worker 数 = CPU 核数，总线程 ≈ 32，WS 1 进程
.venv\Scripts\python.exe scripts\run_servers.py

# 明确指定（生产）
.venv\Scripts\python.exe scripts\run_servers.py --workers 8 --threads 8 --no-reload

# 只要 HTTP / 只要 WS
.venv\Scripts\python.exe scripts\run_servers.py --no-ws
```

| 参数 / 环境变量 | 默认 | 说明 |
|----------------|------|------|
| `--workers` | CPU 核数 | HTTP worker 进程数（**多核吞吐主要靠它**） |
| `--threads` | 自动（总线程≈32） | 每 worker 线程数（I/O 等待用） |
| `WEB_CONCURRENCY` | 由启动器写入 | 进程数，用于分摊背压预算 |
| `DB_MAX_CONCURRENT_REQUESTS` | 32 | 全局并发预算（所有 worker 合计）；建议 ≥ workers×每 worker 峰值并发，否则尾延迟被背压排队拉高 |

**启动器自带连接预算自检**（压测教训，见 `docs/压测验收报告.md` §5.1）：
`workers × threads × 2 + 20 ≤ max_connections`，超限会打印安全参数建议——
`CONN_MAX_AGE` 使连接随线程滞留，超预算就是 `too many clients` 500 雪崩。
| `CHANNEL_LAYER_BACKEND` | postgres | 推送通道层：postgres / redis / memory |
| `CHANNEL_POLL_INTERVAL` | 0.1 | postgres 通道层拉取间隔（推送延迟上限） |

前端代理不变：vite / nginx 仍是 `/api` → 8000、`/ws` → 8001。

## 7. 已知取舍 / 下一步

- **WS（daphne）暂为 1 进程**：推送是信号型（客户端去抖 1.5s），I/O 密集不吃 CPU；
  若将来 WS 成为瓶颈，可按同样思路多进程 + nginx 多 upstream 分流。
- **推送延迟 ≤ `CHANNEL_POLL_INTERVAL`**（默认 100ms）：信号型推送足够；要更低延迟调小该值或换 redis。
- **通道层容量**：进程内队列满时丢最旧一条（容量保护）；跨进程未投递消息按 `expiry`（60s）清扫。
- 再往上（>50 并发 / 连接吃紧）：PgBouncer(transaction pooling) → 读写分离 → Redis 缓存，
  判断标准见 docs/数据库优化.md §5。
