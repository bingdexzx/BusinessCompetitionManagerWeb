## 3. 模块化体检

### 已修：权限口径 4 处复制 → 1 处
`basedata/fiscal/regions/stock` 四个 `views.py` 各自复制了一份**逐字相同**的 `_require_member`
（成员/超管判定）。这类复制最危险——改一处漏三处会导致权限口径漂移。现收敛为
`apps.common.authority.can_read_competition()`，四处只保留一行委托。

### 发现但**未改**（需产品/性能确认，列为后续项）
| 问题 | 证据 | 建议 |
|---|---|---|
| 超长函数 | `stock/engine.py:advance_one_stock()` **502 行**、`generate_market_maker_orders()` 326、`advance_round()` 125、`basedata/views._replace_relations()` 104、`build_candle()` 98、`build_sync_payload()` 94 | 按「取快照 → 撮合 → 定价/涨跌停 → 落账 → 推送」拆成私有阶段函数；**必须先补该链路的针对性测试再动**（撮合/涨停/乐观锁细节多，风险高） |
| 视图层直接 ORM 偏多 | `stock/views.py` 31 处、`regions/views.py` 27、`basedata/views.py` 19、`settlement/views.py` 15 | 逐页把「多表组合/事务」下沉到 `services.py`，简单单表查询保留在视图 |
| `_err()` 9 个 app 各自实现 | 8 个是 `_err(code, message)`，`settlement` 是 `_err(message, code=400)`（签名还不一致） | 低优先；若要统一，先统一签名再加 `apps/common/responses.py`，否则改动面大于收益 |
| 前端超大组件 | `MapsManager.vue` 2,529 行、`ContractDetailView.vue` 1,242、`CompetitionDetailView.vue` 1,180 | 抽 composable（`useMapCanvas`/`useNodeEditing`）与子组件（报告分区、账本分区）；纯结构调整，建议独立一轮做并逐块截图核对 |
| 比赛域 → 全局域 import | 31 处（`competitions`/`packages`/`memberships` 等） | **合理**：比赛库需要读全局元数据。仅注意不要反向依赖比赛域模型 |

### 分层结论
- 全局域 / 比赛域分库与路由（`CompetitionDatabaseRouter`）边界清晰，比赛域模型不建跨库外键。
- `apps/common` 承担权限、上下文、广播、错误、中间件，被两侧复用，职责单一。
- 主要技术债集中在**比赛域的超长函数**与**前端 3 个超大视图**，均已在表中给出拆分路径。

## 5. 注释约定（后续维护请遵守）

**必须保留**（压到 1–2 行即可）：
1. 决策编号与出处：`D1/D9/D13/D14`、`§x.y`、规范/文档引用。
2. 权限口径：谁能读 / 谁能写，以及**为什么这样拆**（可查看 vs 可操作）。
3. 踩坑记录：如「此前 XX 会 YY」「必须用 A 而非 B」「`round2` 必须 `localcontext(prec=70)`，否则现金清零」。
4. 并发/事务/性能取舍：连接复用、`DISTINCT ON`、keyset 分页、推送只当信号 + 去抖。
5. 迁移/兼容注意：旧键 `industryFieldId→industryFieldKey`、脏值 `'undefined'` 清理。

**应删除**：复述代码的旁白、ASCII 分节横幅、历史变更叙述、`Args/Returns` 罗列、显而易见的注释。
