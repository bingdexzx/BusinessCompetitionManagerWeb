# 数据库优化指南（PostgreSQL 多库架构）

> 配套代码：`BusinessCompetitionManagerWeb/settings/databases.py`（连接层优化）、
> `apps/competition/contracts/models.py`（同步索引）。本文说明**已做的优化**与**继续优化的建议**。

## 1. 已落地的优化

### 1.0 运行拓扑（最重要，压测实测得出）

| 发现 | 实测 | 结论 |
|------|------|------|
| Django 同步视图在 **ASGI（daphne）下按线程敏感单线程执行** | `/api/health` 32 并发：daphne **71.7 QPS** vs waitress(WSGI) **909.7 QPS** | **HTTP 必须走 WSGI 多线程**；ASGI 只承担 WebSocket |
| 新建 PG 连接固定 **~44ms**（后端进程启动开销，与 sslmode 无关），复用后查询 **~0.03ms** | 单请求无复用时 health 88ms | **连接必须复用**（`CONN_MAX_AGE=60`） |
| Django 每线程一条连接，复用会随线程数滞留 | 60 并发 ×(全局库+比赛库) > PG 默认 100 → `too many clients` 500 | **`max_connections ≥ 2×并发线程 + 余量`**（本机已调 200），并配**背压限流** |
| 单进程 Python GIL 上限 | 闭环无思考时间 60 并发 ≈ **95 QPS** 吞吐天花板 | **多进程扩展**：prefork 多 worker 已落地，1/2/4 worker 实测 1077/2211/4006 QPS（近线性），见 `docs/多核并发与吞吐优化.md` |

一键启动（HTTP/WS 分端口；HTTP 为**多进程 prefork**，worker 数默认 = CPU 核数）：

```powershell
.venv\Scripts\python.exe scripts\run_servers.py     # HTTP :8000(waitress, N 进程 × M 线程) + WS :8001(daphne)
```

前端开发代理已按此分流（vite `/api`→8000、`/ws`→8001）；生产 nginx 同样分流。

### 1.1 连接层（settings/databases.py）

| 项 | 配置 | 作用 |
|----|------|------|
| `CONN_MAX_AGE=60`（可用 `DATABASES_CONN_MAX_AGE` 覆盖） | 长连接复用 | 新建连接 ~44ms/条（实测），复用后 ~0.03ms；前提是 `max_connections ≥ 2×并发线程` |
| `CONN_HEALTH_CHECKS=True` | 取连接前探活 | 避免复用到被服务端断开的死连接导致偶发 500 |
| `OPTIONS.connect_timeout=5` | 连接超时 | DB 不可用时快速失败，防止请求线程长时间挂起堆积 |
| `OPTIONS.keepalives_*` | TCP keepalive | 及时发现 NAT/防火墙静默断开的空闲长连接 |
| **背压限流中间件**（`DatabaseBackpressureMiddleware`） | 并发请求 ≤ `DB_MAX_CONCURRENT_REQUESTS`（32，**全局预算**，按 `WEB_CONCURRENCY` 分摊到每 worker） | 连接峰值≈64+后台，永远打不满 max_connections；加 worker 不放大峰值；超出排队 10s→503 快速失败（防「后期卡死」雪崩） |
| 竞赛库配置克隆全局库 | `competition_db_config()` | 全部 `comp_<id>` 库自动继承上述优化 |

### 1.2 查询层（增量同步 + 索引）

| 项 | 说明 |
|----|------|
| 合同增量同步接口 | `GET .../contracts?updatedAfter=<ISO>`：只返回 `updated_at > 游标` 的变更，响应携带 `serverTime`（下次游标，规避客户端时钟偏差）、`hasMore`（分批续拉） |
| 同步索引 | `idx_contract_updated_at`（增量扫描）、`idx_contract_status_updated`（状态+时间组合查询） |
| 前端增量合并 | 合同工作台首次全量、此后按游标增量合并（按 id 幂等覆盖）；WebSocket 合同通知到达时只拉增量；失败自动回退全量 |
| 既有索引 | 字段日志 `(company, field, occurredAt)` / `(contract)` / `(operator, occurredAt)`、网络日志 `(user, occurredAt)` / `(device, occurredAt)` / `(traceId)`、字段值 `(company, fieldKey)` 等（只增日志表按检索路径建索引） |

## 2. PostgreSQL 服务端建议（按需调整 postgresql.conf）

| 参数 | 建议起点 | 说明 |
|------|---------|------|
| `shared_buffers` | 物理内存的 25%（如 8GB 机器 → 2GB） | 常用数据缓存，改后需重启 |
| `effective_cache_size` | 物理内存的 50%–75% | 给优化器的「系统缓存」估计值，仅影响计划 |
| `work_mem` | 16MB–64MB | 排序/哈希操作内存；**按连接数放大**，勿激进（100 连接 × 64MB = 6.4GB） |
| `maintenance_work_mem` | 512MB–1GB | 建索引/VACUUM 用，显著加速迁移 |
| `max_wal_size` | 2GB–8GB | 减少 checkpoint 频率（写多的导入场景受益） |
| `autovacuum_vacuum_scale_factor` | 0.05–0.1 | 大表（field_logs/network_logs）默认 20% 才触发，建议调低 |
| `log_min_duration_statement` | 500ms | 慢查询日志，用于定位 N+1 与缺索引查询 |
| `max_connections` | 100→按需 | 见下节连接数估算 |

## 3. 多库架构的特别注意（决策 D1）

1. **连接数估算**：Django 每个线程可同时持有全局库 + 当前比赛库 2 条连接。
   `上限 ≈ (并发线程数 × 2) + 后台任务`，其中 `并发线程数 = workers × threads`
   （`scripts/run_servers.py` 默认自动 ≈ 32）。例如 4 worker × 8 线程 = 32 并发线程
   ≈ 64 连接，`max_connections` 建议 ≥ 100 并配合 **PgBouncer（transaction pooling）**。
2. **只在比赛上下文访问比赛库**：路由层已强制（无上下文直接抛错），避免连接被无关请求打满；
   `CONN_MAX_AGE` 使每个进程复用连接，比赛库数量很多时也不会为每场比赛常驻连接（惰性建立、复用）。
3. **比赛库回收**：比赛结束后归档/删除 `comp_<id>`（`DROP DATABASE` 前先 `pg_dump`），防止库与连接无限增长。
4. **迁移策略**：新比赛库 `CREATE DATABASE + migrate` 全套表（已自动化）；存量库新增索引/字段用
   `provision_competition_db` 补迁移；DDL 期间 `maintenance_work_mem` 调大可加速。

## 4. 应用侧持续优化清单

- **N+1 查询**：列表接口用 `select_related/prefetch_related`（现有合同详情已做）；新增接口用
  `django-debug-toolbar`/慢查询日志定期排查。
- **分页与上限**：所有列表接口有 `limit` 上限（网络日志 200、合同同步 1000）；避免 `SELECT *` 大 JSON。
- **只增日志表归档**（决策 D20）：`field_logs`/`network_logs` 只增不删，保留期 3 年——到期把旧分区
  导出冷存储后删除；建议按月做 `pg_dump` 归档脚本，配合 `autovacuum` 调低阈值。
- **批量写入**：效果审计/字段日志写入用事务批量（当前单合同内事务已保证）；大批量导入（比赛包）可考虑
  `bulk_create(batch_size=500)`。
- **监控**：关注 `pg_stat_activity`（连接分布）、`pg_stat_user_tables`（seq_scan vs idx_scan）、
  慢查询日志；应用层统计接口耗时（网络日志已记录 durationMs，可按 path 聚合）。
- **备份**：全局库每日 `pg_dump`；比赛库随比赛归档快照（财年末已有业务级备份，DB 级另做）。

## 5. 何时引入连接池/读写分离

- **PgBouncer**：并发 > 50 或 `max_connections` 吃紧时引入（transaction pooling 模式与 Django 兼容性最好）。
- **读写分离（主从）**：只读报表（结算、日志检索）压主库时再上；多库路由需在 `DATABASE_ROUTERS`
  增加读路由映射，属于二期工作。
- **进程内缓存**：合同类型 schema / 公司列表已接入（见 §8）；Redis 经评估**不引入**（零依赖优先）。

### 6.4 留存命令（建议低峰期 cron）

```powershell
# 网络日志：保留 30 天 / 最近 20 万条（按业务审计要求可调大 days）
.venv\Scripts\python.exe manage.py prune_network_logs --days 30 --keep 200000
# 广播流水：保留 7 天 / 10 万条（客户端离线超过窗口会自行全量刷新）
.venv\Scripts\python.exe manage.py prune_broadcast_events --days 7 --keep 100000
# 删除后回收空间（低峰期执行）
psql -c "VACUUM (ANALYZE) logs_networklog"
```

`LOG_DIGEST_MAX_LENGTH` 默认 2000，可用环境变量调小（如 500）以显著缩小日志行宽。

### 6.5 400 人规模的容量结论与下一步

- 当前单机（4 worker × 8 线程、PG max_connections=200）在 2000 合同 + 200 轮股票下，
  热路径 P50 均在 30ms 内、P95 < 100ms，稳态约 280 QPS（合同域）/ 180 QPS（股票域）；
- 400 人同时在线按「每人 2–4 秒一次请求」估算峰值 ≈ 100–200 QPS，**有余量**；
- 若同时在线并发继续上涨：先加 worker（18 核可到 8–12 worker）→ 再上 PgBouncer
  （transaction pooling，`max_connections` 不随线程线性膨胀）→ 最后才考虑读写分离；
- 若网络日志必须保留 3 年：建议按月分区（`network_logs_YYYYMM`）+ 冷数据导出，
  不建议单表无限增长。


## 7. 2026-11 落地：网络日志按月分区 + PgBouncer

### 7.1 网络日志按月分区（保留 3 年）

`logs_networklog` 已从单表改为 **RANGE 分区（按 `occurred_at` 月）**，迁移
`apps/global_/logs/migrations/0003_partition_network_logs.py`：

- 每个自然月一个分区 `logs_networklog_pYYYYMM`；老数据按所在月自动落位；
- 保留 `logs_networklog_default` 兜底，避免「忘记建下月分区 → 写入直接报错」；
- 主键 `(id, occurred_at)`（分区表要求分区键进唯一约束），`id` 仍是 identity 序列，ORM 无感；
- 索引/FK 与模型定义同名（`logs_networ_user_id_c1ab6c_idx` 等），迁移测试通过。

**月度维护（建议每月 1 号 cron）**：

```powershell
.venv\Scripts\python.exe manage.py ensure_network_log_partitions --months 6
```

命令会提前建未来 6 个月分区；若 DEFAULT 里已有目标月份的行，会先搬入新分区再
`ATTACH`（避免约束校验失败）。可用 `--dry-run` 预演。

删除旧数据仍用 `prune_network_logs`（按天/条数），删除后分区内空间可 `VACUUM`。

### 7.2 PgBouncer（并发 > 50 时接入）

配置与部署见 [`deploy/pgbouncer/`](../deploy/pgbouncer/README.md)：

- `pool_mode = transaction`、`max_client_conn = 600`、`default_pool_size = 30`；
- 数据库名用 `*` 通配，全局库与动态比赛库都走同一个 bouncer；
- 应用侧只改 `DATABASES_HOST` / `DATABASES_PORT(6432)`，比赛库配置会克隆全局库；
- transaction 模式下需 `DISABLE_SERVER_SIDE_CURSORS=True`（psycopg2 命名游标跨事务失效）；
- 接入后 PG `max_connections` 可降到 100，服务端连接数稳定在池大小附近。

> 本机（Windows）没有 Docker/PgBouncer 可执行文件，配置未做连通性实测；
> 上线前按 README §5 用 `load_throughput.py` / `load_contract_mgmt.py` 复测。

## 8. 进程内缓存层（2026-11，不引入 Redis）

> 决策：**不引入 Redis**。用 Django 进程内缓存（`LocMemCache`），零外部依赖、零运维。
> 代价是每个 waitress worker 各一份缓存；对目录型数据来说，冷启动开销被消除即可，重复加载可接受。

### 8.1 缓存什么（只缓存目录型数据）

压测发现最贵的读路径是 `GET /contract-types`：每个合同类型都要读插件文件 + AST 扫描 + `exec`，
49 个类型一次 **≈300ms**，而内容只在比赛包导入时变化。公司列表（400 行）也是高频读、低频写。

| 命名空间 | 内容 | TTL | 失效方式 |
| --- | --- | --- | --- |
| `contract-types` | 合同类型 schema | 600s | 比赛包指纹（数量 + 最大 id）变化换 key；`packages`/`plugins` 写操作广播时 `bump` |
| `company-list` | 公司列表（按可见范围 + assigned） | 15s | `companies`/`teams` 写操作广播时 `bump` |

实时数据（合同/股票/字段值/消息）**不缓存**，继续走数据库 + WebSocket 增量。

### 8.2 实测收益（LocMem 口径）

| 接口 | 未命中 | 命中 | 提升 |
| --- | --- | --- | --- |
| `GET /contract-types` | 297ms | **4.4ms** | ≈67× |
| `GET /companies` | 19.0ms | **1.9ms** | ≈10× |

### 8.3 约定（`apps/common/cache.py`）

- **命名空间 + 版本号失效**：key = `{namespace}:v{版本}:{参数}`；失效 = 版本 +1，
  不使用 `SCAN`/`delete_pattern`；
- `remember(namespace, parts, producer, timeout)`：未命中才执行 producer；
- `bump(*namespaces)`；广播中间件按资源自动 `bump_for_resource`；
- **缓存不可用时自动回退数据库**（读写异常只记日志，不影响请求）。

### 8.4 配置与回退

`settings/base.py`：

| 环境变量 | 作用 |
| --- | --- |
| `CACHE_DEFAULT_TIMEOUT` | 默认 TTL（秒），默认 300 |

如需彻底关闭缓存（排查用），把 `CACHES['default']` 换成
`django.core.cache.backends.dummy.DummyCache` 即可，代码无需改动。

### 8.5 后续可继续缓存的候选（按收益）

1. 基础数据下拉选项（原料/零件/产品/地点/城市/载具/公司/区域）——写少读多，按 `basedata` 广播失效；
2. 公司字段定义（`IndustryField`，48 行）——公司表与重算频繁读取；
3. 仪表盘聚合统计——短 TTL 5–10s；
4. 站内信未读数——写时失效、读多。
