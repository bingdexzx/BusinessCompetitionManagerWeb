# 独立压测工具（单文件 .bat）

**只需要 Windows 的 cmd + Python 3.10+**，不依赖 Django、不装任何第三方包，
放在任意目录、从任意位置运行都可以（报告写在 bat 旁边的 `reports\loadtest`）。

## 快速开始

1. 双击 **`loadtest.bat`**（或在 cmd 里直接运行 `loadtest.bat`）；
2. 按提示输入：目标网址 → 超管账号 → 密码（输入不回显）→ 压测模式 → 并发数 →
   持续秒数或请求总数 → 思考时间；
3. 探测接口与压测过程中会显示实时进度条；
4. 跑完在 `loadtest.bat` 同目录的 `reports\loadtest\` 下生成 Markdown + HTML 报告。

也可以直接带参数（适合脚本/CI，写在 cmd 里）：

```bat
# 模式一：固定时长
loadtest.bat --base-url http://127.0.0.1:8000 ^
  --username full_admin --password "***" ^
  --users 20 --duration 60 --think 1 --timeout 30 --yes

# 模式二：固定请求总数（发完 20000 个请求，看总耗时）
loadtest.bat --base-url http://127.0.0.1:8000 ^
  --username full_admin --password "***" ^
  --mode requests --users 50 --requests 20000 --think 0 --timeout 30 --yes

# 模式三：固定 RPS（开环，每秒 100 个请求，持续 60 秒）
loadtest.bat --base-url http://127.0.0.1:8000 ^
  --username full_admin --password "***" ^
  --mode rps --rps 100 --duration 60 --users 50 --timeout 30 --yes

# 按生产访问占比加权（权重文件见 weights.example.json）
loadtest.bat --base-url http://127.0.0.1:8000 ^
  --username full_admin --password "***" ^
  --mode duration --users 30 --duration 60 ^
  --weights weights.example.json --yes
```

> 只要系统有 `py` 启动器或 `python` 在 PATH 里即可；脚本会优先用 `py -3`，
> 避免命中 Microsoft Store 的 python 占位符。

## 参数

| 参数 | 说明 | 默认 |
| --- | --- | --- |
| `--base-url` | 目标网址（http/https） | 交互询问 |
| `--username` | 超级管理员账号 | 交互询问 |
| `--password` | 密码（建议交互输入，避免进历史） | 交互询问 |
| `--mode` | `duration`（按时长）/ `requests`（按请求总数）/ `rps`（固定 RPS 开环） | 交互询问，默认 duration |
| `--users` | 并发虚拟用户数 | 交互询问，默认 10 |
| `--duration` | 持续压测秒数（duration 模式） | 交互询问，默认 30 |
| `--requests` | 固定请求总数（requests 模式） | 交互询问，默认 `max(100, 并发×10)` |
| `--rps` | 固定 RPS（rps 模式，需配合 `--duration`） | 交互询问，默认 50 |
| `--weights` | 流量权重 JSON：`{"接口label": 权重}`；未列出接口默认 1 | 不使用（均匀轮询） |
| `--think` | 每轮请求后的思考时间（秒） | 交互询问，默认 1.0 |
| `--timeout` | 单请求超时秒数 | 60 |
| `--cid` | 指定比赛 ID | 自动挑第一个可用比赛 |
| `--report-dir` | 报告目录（bat 默认传脚本旁 `reports\loadtest`） | 脚本旁 |
| `--insecure` | HTTPS 忽略证书校验 | 关闭 |
| `--no-html` | 只生成 Markdown | 关闭 |
| `--yes` | 跳过开始前确认 | 关闭 |
| `--fail-on-error` | 有错误时退出码非 0（CI 门禁） | 关闭 |

## 三种模式与「巅峰性能」怎么测

| 模式 | 指标 | 适合 |
| --- | --- | --- |
| `duration` 固定时长 | 稳态 QPS、P50/P95/P99 | 模拟持续在线压力、观察长尾与稳定性 |
| `requests` 固定请求数 | **完成 N 个请求的总耗时**、折算 QPS、分接口延迟 | 对比不同并发下的「处理能力上限」、版本前后性能回归 |
| `rps` 固定 RPS（开环） | **实际完成 RPS**、从计划发出时间起算的延迟（含排队） | 验证限流、超时与过载表现；接近真实入口流量 |

`requests` 模式的正确打开方式：

1. **思考时间设为 0**（`--think 0`），否则测到的是业务节奏，不是吞吐；
2. 请求数要足够大，避免启动/探测阶段占比过高；建议至少 `并发 × 接口数 × 3`，
   例如 50 并发 × 80 接口，先跑 20000 个请求；
3. 固定同一请求数，横向扫并发：`--users 10/20/50/100`，看「总耗时」何时不再下降、
   P95 何时开始抬升，那个拐点就是当前环境的吞吐上限；
4. 固定并发，纵向对比版本：同一 `--users`、`--requests`，升级前后各跑一次。

注意：

- `requests` 是**闭环**模式，并发数包含客户端等待时间；它回答的是「这些并发能多快干完 N 个活」，
  不是严格的「每秒固定打 N 个请求」；
- 如果要做 SLO/限流验证（固定 RPS、看超时），用 `rps` 模式；它按固定间隔派发，
  延迟从「计划发出时间」起算，队列等待会体现在 P95/P99 上；
- 短请求数会受 TCP 建连、JIT/缓存预热影响，结论优先看多次运行的中位数。

## 结果能代表生产吗？

**不能直接等同。** 这是一个「当前环境 + 当前数据 + 只读接口」的压测，适合做相对比较和瓶颈定位，
不适合直接当作生产 SLO 结论。

| 维度 | 本地/开发环境 | 真实生产 |
| --- | --- | --- |
| 链路 | 直连 Django（可能绕过 nginx/TLS/PgBouncer） | nginx/证书/PgBouncer/网络延迟全在链路上 |
| 数据量 | 开发库小、缓存热 | 生产库大、冷热不均、索引与统计信息不同 |
| 流量 | 默认 80 个只读接口均匀轮询（可用 `--weights` 加权） | 读写混合、接口权重不均、用户行为有突发 |
| 并发 | 单个压测进程的线程 | 多入口、长连接、WebSocket、限流/WAF |
| 客户端 | 压测机与服务器可能同机，争抢 CPU | 压测机应独立，避免先压垮客户端 |
| 写路径 | 无写请求 | 合同创建/执行/回滚、结算、导入等事务与锁 |

它**能**发现：

- 单接口明显慢、N+1、慢 SQL、序列化过大；
- 版本前后吞吐/延迟回归；
- 当前机器上 waitress 线程数、DB 连接池、PgBouncer 的瓶颈趋势；
- 不同并发下的吞吐拐点。

它**不能**直接回答：

- 「生产 1000 人在线会不会卡」；
- 写事务、锁竞争、结算批处理下的表现；
- 跨地域网络、TLS 握手、限流策略下的真实延迟。

### 想更接近生产

1. **同构环境**：独立 staging，使用与生产相同的 nginx/TLS/PgBouncer/PostgreSQL 配置、
   worker 数、CPU/内存；
2. **独立压测机**：不要和服务器抢 CPU；必要时多台压测机分担并发；
3. **生产量级数据**：导入接近真实规模的公司/合同/日志，分别测冷缓存与热缓存；
4. **按访问日志配权重**：真实用户不会均匀轮询 80 个接口，按生产请求占比给接口加权；
5. **补写场景**：在可回滚的 staging 上压合同创建/执行/回滚、结算预览等写路径；
6. **同时看服务端**：CPU、内存、PG 连接数/锁等待、PgBouncer `SHOW POOLS`、nginx 5xx；
7. **固定 RPS 的开环压测**：用 `--mode rps --rps N --duration T` 验证限流与超时；
8. **多轮取中位数**：每档并发至少 3 次，排除预热和偶发抖动。

> 结论写法建议：「在当前 staging（4 worker × 8 线程、PgBouncer、数据量 X）下，
> 50 并发固定 2 万请求耗时 Y 秒，P95=Z ms；相较基线版本提升/下降 N%。」

## 进度与反馈

- 登录后先显示 `探测 [####----] 42%  3/8 合同列表`；
- 压测开始后显示实时进度：`压测 [######----] 60%  18/30s  请求 952  错误 0  QPS 52.1`；
- 非 TTY 环境（CI、重定向到文件）自动关闭进度条，避免日志刷屏；
- 指定 `--yes` 时使用默认并发/时长，不交互询问。

## 压测哪些接口

登录后按以下范围**自动探测**，只保留返回 200 的只读接口（全部 GET，不写数据）：

- **全局**：健康检查、比赛列表、当前用户、版本、更新日志、我的获奖/票据/奖牌/设备、
  收件箱/发件箱/通讯录、学校、用户、插件注册表、网络日志、设备、限流配置/记录、奖牌管理；
- **比赛**：比赛详情/meta/权限/仪表盘、公司、队伍、成员、邀请、作业、合同类型/列表/增量、
  产业与产业字段、比赛包、财年、区域/地图概览/区域字段、消费者需求、股票行情/同步/市场/盘口/
  委托/账户、字段日志、审计流水、结算配置/候选/结果、获奖名单/发放、定时器、比赛消息；
- **数据管理**：fuels、warehouses、vehicles、maps、materials、products、parts、
  infrastructures、tech_tree、production_lines；
- **详情样本**：先取列表第一条，再探测公司实体表/财务报表/产业字段/区域、合同详情/效果/台账、
  区域详情/总览卡片、财年备份、股票详情/K 线、队伍详情。

> 取不到样本或接口返回 403/404 时自动跳过；可用接口数量、跳过原因会在控制台输出。
> 目前完整环境可覆盖约 80 个只读接口。

## 报告

```
reports\loadtest\loadtest_20261125_160100.md    # 文本（可贴群/入库）
reports\loadtest\loadtest_20261125_160100.html  # 浏览器直接打开
```

内容：目标/账号/比赛/并发/思考时间 → 总体指标（QPS、错误率、P50/P95/P99）
→ 分接口表（含状态码分布）→ 自动结论与建议。

## 报告怎么看

以一份真实报告为例：

```
- 模式：固定 RPS（开环）
- 目标请求数：2500
- 目标 RPS：50.0
- 并发用户：100　思考时间：0.1s
- 实际耗时：50.1s
- 可用接口：19 个（健康检查、比赛列表、……）
```

### 头部参数

| 字段 | 含义 |
| --- | --- |
| 目标地址 / 账号 | 压的是哪个环境、哪个账号；账号权限决定能探测到多少接口 |
| 比赛范围 | `未指定` = 只测全局接口；填了 `--cid` 才会测比赛内接口 |
| 模式 | `duration` / `requests` / `rps`，决定下面的指标怎么解释 |
| 目标请求数 / 目标 RPS | 计划值；`rps` 模式下两者相乘约等于实际耗时 |
| 并发用户 | 同时干活的 worker 数（rps 模式下是最大并发） |
| 思考时间 | 每个请求后的停顿；测吞吐时应为 0 |
| 实际耗时 | 从第一个请求到最后一个请求完成 |
| 可用接口 | 探测后真正返回 200 的接口；数量少说明权限/比赛/版本不匹配 |

### 总体指标

| 指标 | 含义 | 怎么判断 |
| --- | --- | --- |
| 总请求数 | 实际完成请求数 | 应等于目标；偏小说明有请求未完成 |
| 吞吐 QPS | 总请求数 ÷ 实际耗时 | `rps` 模式下应接近目标 RPS；明显偏低说明没打满/客户端瓶颈 |
| 错误数 / 错误率 | 连接失败 + HTTP 5xx | 4xx 不计入 error，但会出现在状态码里 |
| P50 | 一半请求快于该值 | 日常体验的基线 |
| P95 | 95% 请求快于该值 | 主要看这个；<200ms 健康，200–500ms 需关注，>500ms 偏高 |
| P99 | 99% 请求快于该值 | 长尾；P99 远高于 P50（>5×）说明有排队/锁/慢查询 |

### 分接口表

| 列 | 含义 |
| --- | --- |
| 接口 | 探测到的接口名 |
| 请求数 | 该接口被打了多少次；均匀轮询下应接近；用 `--weights` 后按权重分布 |
| QPS | 该接口的每秒请求数；所有接口 QPS 之和 ≈ 总体 QPS |
| P50 / P95 / P99 | 该接口自己的延迟分布 |
| Max | 最慢一次；偶发高不一定是问题，持续高要查 |
| 错误 | 该接口的连接失败 + 5xx 数 |
| 状态码 | `200×N` 等；出现 401 说明 token 失效，403 说明权限不足，5xx 说明服务端异常 |

### 用这份报告举例子

- `目标 RPS 50`、`总请求 2500`、`QPS 49.9`：调度基本打满，客户端不是瓶颈；
- `P50 47ms / P95 97ms / P99 112ms`：整体健康，长尾不严重；
- `网络日志 P95 148ms` 是分接口里最慢的，继续加压时优先观察它；
- 个别接口 `Max 350ms` 是偶发尖刺，样本量小时可先记录、多跑几轮确认；
- `比赛范围：未指定` 导致只有 19 个全局接口；要测比赛内的公司/合同/股票，传 `--cid` 或先选一个比赛。

### 找吞吐拐点

- `rps` 模式：逐步提高 `--rps`，直到「实际 QPS 明显低于目标」或「P95 持续抬升 / 出现 5xx」，
  该点就是当前环境的吞吐上限；
- `requests` 模式：固定请求数，提高并发，看总耗时何时不再下降；
- 两种方式都建议每档至少跑 3 次，取中位数。

## 实现说明（维护用）

- `loadtest.bat` 是**单文件版**：前半段是批处理（找 Python → 用 PowerShell 把内嵌源码抽到
  `%TEMP%` 执行 → 删除临时文件），后半段是完整的 Python 源码；
- 源码在 `loadtest.py`；修改后运行 `python build_bat.py` 重新生成 `.bat`；
- 报告目录不可写时（如 bat 放在只读位置），会自动退回 `%USERPROFILE%\bcm_loadtest_reports`。

## 注意

- 只读压测（全 GET），不会创建/修改/删除数据；
- 默认 10 并发 × 30s，建议先小规模试跑再逐步加压；
- 压测时后端请用 `run_servers.py --no-reload`（开发热重载会中途重启 worker，长尾数据不准）；
- 超管密码不要写进脚本/仓库，建议交互输入。
